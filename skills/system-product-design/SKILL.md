# 系统产品设计

把系统做成新人能上手、熟手能高效反复进入、找到对象、完成任务并接着处理结果的工作空间。产品结构和操作组织优先于视觉装饰。系统完整度以真实用户能完成工作衡量，不以功能数量衡量。

本包可独立使用；以本 `SKILL.md` 为执行规范，设计原则概览见 [设计原则](references/design-principles.md)。需要理解工作台组织方式时读 [内容工作台示例](references/workspace-example.md)。写规格时可用 [关键任务卡与模块表](references/task-spec.md)，合并到项目已有文档，不为填模板增加业务模块。首次使用体验按 [入门与持续帮助](references/onboarding.md)；设计日常使用或真实运行时读 [完整性与运行条件](references/system-readiness.md)。按需读取相关材料，不扫描整个知识库。相邻 skills 仅在已安装且适用时使用，不作为本包的安装前置条件。

## 与 AI Coding 总流程的关系

本 skill 可作为 `ai-coding-workflow` 或项目已有开发流程的系统产品设计阶段，也可独立使用，保留全部独立触发入口及默认交付能力。总流程遇到系统新建/结构重做时自动读取本规范，用户无需再次触发；已有局部迭代只取受影响内容，纯后台修复与小修改不强制整套设计。

产品设计的详细规则只在本 canonical skill 维护。总流程负责范围、开发推进、当前版本证据、交接和经验；本阶段负责系统对象、任务、模块、双端与入门体验，将相关产物和任务验收标准传给后续开发/验证。承接已有目标、决定与资料，不重复访谈或另建一套规格。

单独说「系统产品设计」「按第二种搭系统」「做成真正的系统」「把页面升级成系统」「电脑和手机都要像系统」仍使用本 skill。只要求设计或比较时交付对应设计，不自动回到总流程启动开发台账、实现或部署；已要求原型或真实实现时仍推进到原终点。两种入口沿用同一份详细设计规范，不互相循环调用。

## 1. 承接已有上下文

- 先找项目现有方案、原型、数据结构和相关项目决策与知识库记录。已确认信息直接沿用，不重复访谈。
- 明确主要用户、进入时机、输入、日常动作、产出及结果接收者。缺信息时只问影响设计的关键问题，并继续独立工作。
- 沿用系统业务 Owner、架构师和可核验定量目标；缺项明确待确认，可继续设计草案，不伪报正式建设或验收。
- 用户要设计比较就交付比较与规范；要搭系统则把设计落成可操作结果，不能停在提纲。只改局部时按影响范围处理。

开始时用一句话明确本次终点、已有项目/技术栈和设备范围，从请求与上下文推断，不重复求确认。设计、可操作原型、真实接入、部署分别核验；用户已要求真实接入/上线时，不能以原型完成结案。缺 Owner 或目标时继续可独立完成的设计/开发，明确草稿状态，不把缺项变成停工理由。

用简短的完成定义承接范围：主要用户、最重要任务、实际结果、交付阶段、设备/语言、依赖与验收证据。区分每套新建系统的基础能力和按业务风险适用的能力（见完整性参考），不把所有建议都变成新模块。可主动提出少量能消除具体使用障碍的改进，说明收益和代价；已有授权内的基础设计直接落地，超出范围的新业务能力明确列为可选，不暗中扩展需求。

用户提供参照图或明确框架时，先提炼入口、行为、角色和设备要求，并逐项对应实现位置与验收证据；沿用 [关键任务卡与模块表](references/task-spec.md) 的简表，区分用户明确要求、设计建议和纯外观参照。不能只凭“风格类似”判定完成，也不把图中全部装饰或业务模块变成通用硬模板。

本 skill 承接原任务：PRD 继续由 `system-prd` 主导；已授权开发/改造继续已有平台与技术栈；明确选妙搭才加载妙搭路径。只读取相邻 skill 的相关阶段，不循环重开访谈、立项、台账或平台选择。局部修复不扩大为整体重做，开发授权也不自动等于对外发布授权。

## 2. 定义业务对象与状态

建立核心对象表：对象名称、身份/唯一标识、关键字段、来源、关联对象、状态、允许动作、结果去向。

同一对象应在列表、详情、编辑器、审核队列和统计中保持一致。已生成、已保存、已提交、已审核、已导出、已绑定链接、已发布分别建模，只有对应动作发生并有证据时才改变状态。

状态转换按业务需要写清前置条件、执行角色、接手人/队列、结果落点、失败后去向。协作任务验证「甲提交→乙在自己的队列找到同一对象→处理/退回→甲继续」；单人任务不强加审核角色。前端角色切换不等于真实权限验证。

为有用户输入的关键任务说明：草稿/保存/提交的时机、当前会话/本机/后台的保存范围、离开与再次进入的恢复方式。处理未保存编辑、失败重试和重复提交，避免静默丢失内容或重复业务结果；不能只弹「已保存」。上传/批量/后台生成适用时考虑部分成功、重试和结果找回，不强加无关功能。

用真实数据或明确的待登记/待接入状态；不编造人员、价格、使用次数或完成结果。示例数据如确有需要，显式标为示例，不能冒充经营事实。

## 3. 设计模块地图和稳定导航

按用户工作组织模块，可参考创作/资产/流程/管理，但不机械照搬名称或数量。

- 每个主要模块有独立目的和核心对象或任务。
- 对需要管理的对象设计列表/检索→详情→操作→结果层级；不为凑完整度虚构页面。
- 系统外壳提供稳定导航、当前模块、搜索/新建等常用入口；详情和编辑场景提供返回路径或面包屑。
- 切模块、进入详情、进入编辑器时保持对象与必要筛选上下文。返回不应让用户无故从头开始。
- 首页优先放主要用户高频动作、对象库或工作队列。日常任务按业务需要区分「需我处理、等待他人、被阻塞」，展示原因与下一步；只有存在真实时限才展示逾期。数据分析按角色需要安放，不默认把所有系统首页做成 KPI 看板。

用模块覆盖表列出本次承诺的入口、对象、主要动作、结果与状态：`已接入 / 可交互原型 / 待接入 / 本次不含`。所有承诺入口可达，每个本次实现模块有可工作的主要任务。待接入入口展示真实状态与缺口，不用空页面、假数字或只弹成功提示冒充功能；一条流程通过不能代表全系统完成。

## 4. 让第一次进入的人会用

新建系统默认交付产品内「开始使用」板块和稳定的帮助入口，改造时复用已有入口；局部修复只处理受影响内容。可以是首页区块或轻量页面，不强制新增一级导航。用户已有明确范围例外时遵从并标出，不默默省略。

- 用业务语言说明为谁解决什么问题、主要产出及已接入范围，避免技术介绍或欢迎标语替代教程。
- 展示简短工作流：输入/准备→主要步骤→结果→接手者/下一步；多角色时说明各自负责什么，步骤名称与实际模块/状态一致。图旁提供可读的文字步骤，手机同样清楚。
- 给主要角色一条快速开始路径，写出需要什么、点哪里、完成后到哪里找结果；主按钮直达真实可用功能。已知账号身份就沿用，不为教程虚构角色选择或申请权限流程。
- 允许跳过/关闭和随时重看；记住已看/跳过及必要的进度，明确本机/账号保存范围。再次进入优先日常工作，不反复强制教学；跳过引导不等于任务完成。首次使用功能时再提供就近提示。
- 初次空状态给第一步行动；无权限、未接入、无搜索结果分别说明原因和下一步。必要设置与可选教学分开；确实阻断业务的前置条件说明原因和接手者，不能让无权限的人反复尝试。
- 练习数据如需提供，要明确隔离且不混入经营事实；引导本身不自动提交、发送、付款或发布。真实业务动作沿用其权限和确认规则。

按入门参考验收首次显示、跳过、重开、回访和第一项任务结果；流程/字段/路由改动时同步改教程。引导应减少学习成本，不能用来掩盖复杂导航或未实现功能。

每个主要角色严格照产品内教程走完首项任务，逐步记录实际入口、按钮、结果对象及回读。不能用搜索结果捷径、后台接口、设计者记忆或口头补充绕过教程中缺失的步骤；发现文案所述入口不存在、权限不符或结果找不到，即判该路径未通过，修复后重走。教程走查与后台功能验证分别记录。

## 5. 为关键任务设计工作台

先画最重要的场景，再扩展功能页。每条路径写清入口、输入、操作、反馈、结果对象、下一步；同时考虑异常修复后如何继续。

- 让输入、预览和反馈保持可理解的关系。编辑器、审核队列、资料库应按不同任务选择布局。
- 每个任务状态有明确主操作；按钮文案描述动作与结果，例如「生成 4 张」「提交审核」。无需强迫只读资料页出现无意义操作按钮。
- 规则在影响操作的位置出现，并提供可执行修复路径。例如锁价缺失→对应记录→完成后回到原任务。
- 大段背景、技术说明放进帮助、来源详情或关于页面；影响决策的数据时效、缺失和限制仍要就近展示。
- 空状态、搜索无结果、处理中、失败、无权限或缺少必需信息，给出真实状态和可行的下一步。

主要页面写清谁用、核心对象、目的、布局、主/次动作、校验、加载/空/异常状态及结果落点。导航、控件、间距和层级保持一致；图像浏览让图像突出，记录处理保留合适的信息密度，不把所有模块套成大标题加卡片墙。

让核心结果按名称/业务标识找回，详情能解释来源、关联输入与关键变化；版本覆盖风险存在时保留版本关系，必要时可分享的对象直链沿用权限检查。长任务展示真实阶段和可行的取消/重试/离开后找回方式；不知道进度就不编百分比。

AI 参与核心任务时说明输入来源、输出对象、用户修订/重试、人工接手和失败处理；固定规则、模板合成与演示动画按真实能力标注，聊天框本身不能代替业务流程。

## 6. 电脑和手机分别设计交互

两端共享业务语义和数据，分别安排操作布局。默认覆盖电脑与手机；若用户已明确设备范围，以用户要求为准。

| 任务 | 电脑可用方式 | 手机可用方式 |
|---|---|---|
| 全局导航 | 固定侧栏、分组、常驻搜索 | 底部导航或简洁菜单，详情返回；按模块数量选择 |
| 编辑 | 素材/对象、画布、属性并排 | 预览加工具页签/分步编辑，主操作持续可达 |
| 对象检索 | 表格、筛选、排序、详情侧栏 | 重点字段列表、筛选面板、独立详情 |
| 结果与批量任务 | 并排比较、批量操作 | 单项重点查看、合理横滑、明确选择数量 |
| 补充信息 | 侧边抽屉或弹层 | 底部抽屉或详情页，避免遮挡主要动作 |

手机不能只把电脑页缩小或依赖横向拖动宽表格；电脑也不应浪费宽屏、把所有操作排成长表单。底部六个按钮、手机外框和固定三栏都不是硬模板，选择取决于任务。

用户明确要求，或本次已承诺桌面查看/培训移动端的场景时，提供产品内“手机版长什么样”入口；新识别的场景先说明收益与成本，不能默默扩展范围。优先加载实际手机页面，共用数据、对象和权限；静态示意或模拟页标清边界和版本。预览内的导航与操作范围需说明并验证，不以手机外框证明双端适配或真机已通过。

桌面检查宽度与常用窗口高度，手机检查内容、导航和主操作的可达性。新增帮助、手机预览或账号入口后，确认主导航没有被挤掉、遮挡或藏进难以发现的局部滚动；长导航可滚动，但当前项与常用入口仍应容易找到。

同一任务列清电脑/手机分别怎么完成、共享哪些对象与状态、有意限制及原因。不能默默省去手机关键动作，也不强制业务上不需要的功能完全相同。

检查触摸操作不依赖 hover、输入时主按钮/错误信息可达、键盘焦点与标签可用、状态不只靠颜色。窄屏模拟不等于真机；软键盘或真实触摸未测试就注明，继续其他可验证工作。

## 7. 实现、运行与相邻 skills 衔接

- 方案/PRD 任务由 `system-prd` 主导，本 skill 提供产品结构与交互；纯设计/开发请求不自动扩大为整套 PRD、台账和文档发布。
- 沿用项目的品牌与语言规范；如已安装对应品牌 skill，可按需读取。对项目要求的每种语言检查动态内容和关键路径。
- 妙搭开发与发布按 `lark-apps`/`creative-design`；已有项目优先复用其代码、数据、技术栈和现有验证方式。采用当前平台提供的安全工具，接口优先。
- 涉及版本记录时按 `ui-version-sync`；纯 BI 看板按 `bi-spec` 或对应分析流程，不强加业务系统外壳。
- 原型可用单文件 HTML；文件数量不等于系统成熟度。保留现有真实数据和验证逻辑，不为换外观重造假数据。
- 本地模拟、前端身份切换、AI 占位、真实后台分别标清。原型完成不能等同于通知送达、权限生效或生产上线。

改造已有系统前记录原数据源、对象标识、业务规则与主要路径；完成后检查没有因换外壳丢掉已有能力。

按 [完整性与运行条件](references/system-readiness.md) 选择适用项：多人系统检查真实权限与必要的并发冲突处理；外部数据说明更新时点、失败和过期状态；真实运行交付补启动/重启、依赖故障、数据恢复、运行责任人与现有支持入口。保留到项目已有交付材料，不另造运维平台。上线之前沿用原授权，不因本 skill 自动启用外发通知、采集行为数据或定时任务。

**登录一律用飞书账号**（本规范的组织默认，适用于本规范下的系统）：默认飞书账号登录（网页 OAuth 授权，或飞书客户端内免登），**不设用户名/密码**，不用 nginx Basic Auth、共享口令或自建账号体系。

- 身份以飞书返回的 union_id（同租户各应用一致）为准，open_id 只在同一应用内用；角色由服务端按飞书身份映射（名单、部门、门店账号等业务规则）。未开通的人只看到「未开通」说明和联系人，看不到任何数据。
- 会话用服务端签名的 HttpOnly Cookie 并设过期；页面、接口、照片/附件、导出都在服务端校验会话，不靠隐藏页面或前端判断。
- 飞书应用的重定向 URL、可用范围和 App Secret 属于管理员操作：只准备配置位置和操作清单，不读取、不回显、不解密密钥；这些步骤没完成时系统显示「飞书登录待开通」，不退回用户名密码凑合上线。
- 支持账号/角色视角预览时，真实登录身份与预览身份分别显示，并分别在服务端鉴权；只有已授权管理员可选择其他人的视角，目标账号按其实际有效权限读取。预览默认只读，服务端拒绝保存/提交等写入，不能靠禁用按钮保证只读，也不能修改其他标签页的登录或预览状态。若原业务明确授权可写预览，须另行说明动作、对象、风险及审计，记录真实执行者与视角，不能默认代人操作。
- 平台自带飞书登录的（如妙搭）直接用平台能力；本地开发可用模拟身份，但不得带到部署环境。

## 8. 按工作流与独立使用验收

按 [验收清单](references/acceptance-checklist.md) 与模块覆盖表检查：所有承诺导航可达；每个本次实现模块的主要动作可用；关键端到端路径在承诺的电脑与手机上分别操作到结果，并按风险选验异常修复。小系统一条核心路径可以足够，多模块系统不能用一条路径代表全部模块。

使用项目目标设备与断点；无约定时可从 375/390 宽手机视口、1440 宽桌面开始，并查看中间宽度。这是检查起点，不是行业认证或必须照搬的布局尺寸。按项目与品牌要求逐语言检查关键路径。

检查对象上下文、返回、状态变化、跨页面一致性、操作可达性、溢出/遮挡与所需语言。实际修改/生成的结果要回读。没有执行的检查写未验证，不把已有测试脚本当成测试已通过。

记录实际环境/尺寸、步骤、预期/实际结果和证据位置。截图说明布局，操作记录说明流程，保存回读说明状态；按承诺走一次「保存→离开/刷新→重新进入→继续→找到结果」，协作任务再验角色交接。仅有代码、截图或成功提示不能证明完成。

分别列出技术测试、照教程走查、设备模拟/真机与真人独立使用的覆盖和缺口；技术测试数量不能代替体验通过。按 [体验走查与失败案例](references/experience-review.md) 检查参照要求、教程一致性、入口可达及适用的预览边界；维护 skill 时保留相应失败场景，不能只验证成功样例。代码指纹与部署收口沿用项目已有开发交付流程；ai-coding-workflow 如已安装可衔接，不作为本包前置条件，也不复制另一套交付台账。

增加「新人独立完成首项任务」和「老用户再次进入继续工作」两种视角。有人参与时只给任务目标、不口头指路，记录找到入口、完成有效任务、理解结果与下一步的情况及卡点；无人参与时做独立走查并明确未做真人验证。代理模拟不等于真实用户，不能声称所有新人都已会用。

以首项有效任务完成率、完成耗时、卡点/错误恢复和真实工作收益中适合项目的少量指标检验改善，定义口径与来源；目标未定就标待确认，不套固定分钟数或凭浏览教程认定成功。优先现有数据或少量人工观察，不自动安装追踪或收集个人行为。

只针对本次范围做有意义的验证；设计咨询可用图和文字说明，不能宣称真实交互通过。按模块分别报告设计、原型、真实接入、部署、业务接受及剩余阻断；既有“已上线”字样先确认指业务对象发布还是软件部署，分开验证。上线能力另验后台持久化、账号权限、服务调用与发布结果。

## 默认交付

按任务规模组织，复用已有材料，不为形式重复建文件：

1. 模块与导航地图。
2. 核心对象和状态转换表。
3. 关键工作流与异常修复路径。
4. 电脑/手机关键页面与布局差异。
5. 与原请求一致的设计、可操作原型或真实系统（不降低已授权的交付终点）。
6. 入门板块：系统用途、工作流、快速开始、可重看的帮助与首次任务路径。
7. 验收证据、真实接入边界和待完成项；真实运行时附适用的运行/恢复交接。

交付时说明完成了什么、怎么验证及局限。用户要求写入知识库时，优先通过已有文件/API 保存并回读；只有实际可用且已执行的操作才能报告完成。工具能力不足时明确待落地步骤，不假装拥有 Obsidian、飞书或桌面通道。
